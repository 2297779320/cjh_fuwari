这是精读 txp 系列的第三篇了（前两篇是 [V4L2 驱动对象模型](/posts/linux/v4l2-driver-model/)和 [Rockchip DRM/KMS](/posts/rk3588/drm-kms/)）。这篇《对讲完整技术拆解》从产品选型一路讲到量产测试，19 章 1.5 万字，把"把声音传到另一端"这句话背后的工程量拆得清清楚楚。本篇提炼骨架，观点归原作者，原文链接见文末。

## 一、选型先行：先确定"做哪一种对讲"

不同对讲产品的技术方案可能完全不同，三个必须先回答的问题：

- **半双工 PTT 还是全双工免提**：PTT（按住讲话）靠关闭单向收发规避掉大部分回声，软件和声学难度低，适合工业调度和成本敏感产品；全双工（像打电话）体验自然，但 AEC 成为生命线
- **局域网还是公网**：局域网地址可控、NAT 穿透需求低，RTP/UDP 或 SIP 就够；公网设备对 App/浏览器则要面对信令、ICE/STUN/TURN、加密、推送、云端运维全家桶，适合 WebRTC 或云平台 SDK
- **一对一还是群组**：群组意味着 SFU/MCU 媒体服务器、抢麦控制、混音和录音审计

原文给的产品级量化指标表值得抄下来做验收标准，例如：局域网单向延迟 80~150ms、公网 150~250ms；丢包 5% 时公网仍应可继续通话；AEC 双讲时本地语音不应被明显吃掉；XRUN 正常运行应为 0；长稳无内存增长。

## 二、六类方案与决策树

| 方案 | 主要优势 | 主要限制 |
| --- | --- | --- |
| 自定义 RTP/UDP | 轻量、可控、低成本 | 公网和安全要自研 |
| SIP/RTP（PJSIP） | 标准互通、PBX 生态成熟 | 浏览器互通不直接 |
| ONVIF/RTSP | 安防平台兼容 | 不等于完整云对讲 |
| 原生 WebRTC | 公网、加密、跨端能力强 | 体系复杂、资源较重 |
| 云平台 P2P SDK | 闭环完整、上线快 | 平台绑定、定位边界复杂 |
| MCPTT 专业集群 | 优先级、抢占、调度 | 系统复杂、成本高 |

决策树一句话版：只在固定局域网且不需要第三方互通 → RTP/UDP + Opus；需要与门禁/电话互通 → SIP/PJSIP；必须公网浏览器/App 互通 → 自建云端就 WebRTC + 自建信令 + TURN，否则托管 WebRTC 或 IoT P2P 云平台；专业集群调度 → MCPTT。

注意：就算选了"轻量自研"，也不能停留在裸 UDP 发 PCM——RTP 序号/时间戳、乱序去重、Jitter Buffer、PLC/FEC、RTCP 统计、鉴权加密一样都不能少。

## 三、推荐架构与基础格式

原文的核心结论值得整段记住：**WebRTC 是公网设备对 App/浏览器的最佳综合技术主线之一，但它不该替代对 ALSA、AEC、Opus、RTP、Jitter Buffer 和实时调度的学习。产品架构上最稳妥的做法是先建立独立音频引擎，再通过统一接口接入 RTP、SIP 或 WebRTC。**

第一版的基础格式建议统一为：48kHz / S16_LE / Mono，APM 按 10ms（480 样本）处理，Opus 按 20ms（960 样本）组帧，码率 16~32 kbps，Jitter Buffer 初始 40~60ms。数据节奏是 ALSA 每 10ms 出一块 PCM → 前处理 → 攒两块 → 编码一个 20ms 包，兼顾处理粒度、包头占比和 CPU 唤醒频率。

## 四、AEC：全双工的生死线

回声的来源：远端语音 → 解码 → 扬声器 → 空气/机壳 → 麦克风 → 重新上传，远端就听到了自己。AEC 需要两路信号（本地麦克风 + 即将播放的远端参考），估计声学路径再从采集信号里抵消回声。

几条最容易踩的坑：

- **Reference 取法**：必须取接近真正送进 ALSA Playback 的 PCM（解码后、送播前），并且提示音也要进 Reference。拿压缩数据当参考、参考之后又改音量不同步通知 AEC，都是错误做法
- **延迟对齐**是核心变量：从播放队列到采集队列的整条链路延迟都在变化，AEC 需要"有参考"还不够，参考与回声必须时间对齐
- **双讲**（双方同时说话）最难：算法激进会吃掉本地人声，保守则残余回声明显。测试必须覆盖远端单讲、本地单讲、双讲、突然停讲、音量突变、提示音混合等场景
- **声学结构比算法参数更重要**：麦克风与扬声器距离、机壳密封、功放削顶、共地噪声这些硬件问题，AEC 救不了——它只擅长近似线性的声学路径

原文的症状速查表很实用，摘几条：一直有稳定回声 → Reference 没接或格式错；几分钟后开始变差 → 时钟漂移；音量小正常大失败 → 扬声器/功放非线性；单讲正常双讲翻车 → Double Talk 处理不佳。

## 五、NS / AGC / VAD 与编解码

三个前处理模块的能力边界：NS 压得住稳态噪声（风扇、空调），压不住突发碰撞和键盘声，过强会"水下感"；AGC 让远近人声音量稳定，但别用它掩盖硬件底噪——先把模拟增益设到不削顶、信噪比合理，数字 AGC 只做有限补偿；VAD 用于 DTX、PTT 辅助和录音触发，但**不该直接决定播放是否连续**，否则切掉语音首尾。推荐处理顺序：Capture → HPF → AEC → NS → AGC → VAD → Encoder。

编解码结论：G.711 赢在简单省 CPU 和 SIP 兼容性（8kHz 窄带）；Opus 是实时对讲首选（8~48kHz、PLC、In-band FEC、动态码率，公网或丢包场景开 FEC）；AAC 适合音乐和存储，不适合低延迟双向对讲。

## 六、传输：RTP、Jitter Buffer 与时钟

RTP 只提供序号、媒体时间戳、SSRC 这些"信息"，**不保证**不丢包、按序、低延迟——接收侧必须自己补齐。Opus 的 RTP 时间戳按 48kHz 递增，20ms 包即 +960。RTCP 带回丢包率、Jitter、RTT 等统计，只发 RTP 不做反馈闭环的产品级不了。

网络包的到达是抖动、乱序、丢包混合的，正确链路是：UDP 接收 → RTP 解析 → 乱序整理去重 → 自适应 Jitter Buffer → PLC/FEC → 解码 → 定时播放。固定 Buffer（始终缓存 60ms）局域网够用但两头不讨好；自适应 Buffer 根据到达间隔估计网络抖动动态调整目标深度——网络变差逐步加深，变好缓慢回缩（突然大幅缩减会丢帧变调）。WebRTC 的 NetEq 是这方面的标杆参考。

一个容易被忽视的观念：**实时音频的队列必须有上限**。文件下载是一个字节都不能丢，实时对讲是声音必须尽快到达——播放已落后两秒时继续播旧数据没有意义，所有队列（采集环、编码队列、发送队列、Jitter Buffer、播放队列）超限就该丢旧数据回到目标延迟。

时钟方面，系统单调时钟、音频采样时钟、RTP 媒体时间戳三套时间不能混用。播放/采集若来自独立时钟，长期运行必然产生采样率漂移——Buffer 水位持续上升或周期性断音。优先硬件统一时钟（同一 Codec + 同一时钟域），软件侧再配异步重采样、Sample Slip、时间伸缩做补偿。

## 七、WebRTC 架构

建链流程：设备登录信令服务器 → App 发起呼叫 → 双方交换 SDP Offer/Answer → 各自收集 ICE Candidate（经 STUN 探测公网地址，NAT 打不通就走 TURN 中继）→ ICE 连通性检查 → DTLS 握手协商密钥 → SRTP 加密媒体传输。SDP 只是能力和连接信息的描述，不是媒体数据。

拓扑形态：P2P 适合一对一（服务器省带宽）；SFU 转发不混流（主流选择）；MCU 服务端解码混流再编码（适合统一混音输出，成本高）。

嵌入式端的实现选择里，原文最推荐关注 **libdatachannel + 自研音频引擎**的组合：ALSA + WebRTC APM + Opus + RTP/Jitter Buffer + libdatachannel——网络协议层轻量化，音频链路掌握在自己手里。但要清醒：它不会自动替你完成音频引擎，缓存、编码、播放和诊断仍是你的活。

## 八、工程实践：线程、延迟与弱网

**线程模型**：采集 → 处理 → 编码 → 网络发送、网络接收 → 解码 → 播放、信令 → 状态机三条线，可合并但职责要清。实时路径上的禁忌清单：网络阻塞、文件 IO、大量日志、频繁动态分配、长持锁、DNS 查询、JSON 解析——这些都会变成偶发卡顿。配套手段：预分配 AudioFrame Pool、有界 Ring Buffer、短临界区、线程活性的 Watchdog。

**ALSA 参数**别盲目调小 Buffer：过小导致 XRUN 和调度压力，过大增加延迟和 AEC 负担，要在目标延迟和稳定性间找平衡。

**延迟预算**公式：采集 + 前处理 + 组帧 + 编码 + 网络 + Jitter Buffer + 解码 + 播放，参考值合计局域网 100~150ms、公网 150~250ms；超 300ms 明显影响对话，超 500ms 容易互相抢话。调优顺序是先测量各节点时间戳，再逐级确认 ALSA 实际 Buffer、Opus 帧长、Jitter Buffer 目标值、网络排队和各应用队列——不要只盯一个 Buffer 死调。

**弱网**是组合拳：乱序整理 + 自适应 Buffer + PLC + FEC + 码率控制 + RTCP 反馈 + 重连，单纯加大 Buffer 只会加延迟。可按 GOOD/FAIR/POOR/BAD 四级分级：GOOD 降缓存提音质；FAIR 开 FEC 保码率；POOR 降码率加缓存；BAD 直接重连重建链。

## 写在最后

这篇文章最大的价值是把"对讲"从一句需求翻译成了一张可执行的工程地图：选型看场景（双工/网络/人数），架构上音频引擎与协议层解耦，AEC 是全双工的生死线且七分靠声学三分靠算法，传输侧一切围绕"延迟 vs 连续"的动态平衡。和前两篇 V4L2、DRM 一样，先把对象和链路的边界建立起来，再逐层深入，比直接抄 SDK demo 扎实得多。
