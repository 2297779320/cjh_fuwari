上一篇[《从 NV12 到 RGB888》](/posts/linux/nv12-rgb-color/)算的是一组 Y、Cb、Cr 怎样变成 RGB，这篇补上它成立的前提：**怎样证明你取到的恰好是这个坐标的三个样本？** 同一作者的同一系列，从颜色换算退回到内存布局。观点归原作者，原文见文末。

现场开局：1080p NV12 预览，第一行轮廓清楚，从第二行开始逐行错开；把应用里「到下一行」的增量从 1920 改成驱动返回的 2048，轮廓立刻端正，颜色却仍然不对。

为什么改对一处、另一处还能错？因为这里有**两个不同的起点**：下一行 Y 在哪里，看 Y 平面的行距；第一行 UV 在哪里，看 UV 所属的内存对象和它在该对象内的起始偏移。生产端若再用分块或压缩布局，连「向右一个像素加几个字节」都要重新推导。

## 一、把一帧图交给显示窗口，究竟要交什么

一张能上屏的图至少涉及三样东西：**内存对象**存实际数据；**DRM framebuffer（FB）** 记录如何解释这批数据；**KMS plane**（对应 VOP 的窗口）选一个 FB，取其中一块区域参与显示。

应用从摄像头导出一个 DMA-BUF fd，拿到的是共享缓冲对象的引用——**仅凭这个整数读不出宽、高和行距**。登记一个 FB 可以复用已有图像内存，不必把整帧像素再拷进内核一次。

| 布局描述里的信息 | 回答什么 | 具体例子 |
| --- | --- | --- |
| 宽、高 | 像素坐标范围多大 | 宽 8、高 4，x 取 0~7 |
| FourCC | 有哪些分量、怎样打包或子采样 | 线性 NV12 = 一个 Y 平面 + 一个交错 CbCr 平面 |
| 各平面对象引用 | 去哪个内存对象取这部分数据 | Y、UV 可以引用同一个 GEM 对象 |
| Pitch（stride） | 线性平面相邻两行行首相隔多少字节 | 有效行宽 8，行距 12 |
| Offset | 从所属对象开头跨多少字节到平面起点 | Y 从 16 起，UV 从 80 起 |
| Modifier | 这套格式在内存里按哪套规则组织 | LINEAR 逐行；其他规则可能规定瓦片、压缩块或附加数据 |

取左上角四个点 (0,0)、(1,0)、(0,1)、(1,1) 就能检验很多描述：横向移动暴露一个像素或样本组占多少字节，纵向暴露行距，换平面暴露起始位置。**坐标单位写「像素」，地址结果写「字节」**，后面的公式才好读。

## 二、FourCC 的四个字符与一个像素的内容

FourCC 是四个字符构成的 32 位标识，`fourcc_code(a,b,c,d)` 依次放进低 8 位到高 8 位：`DRM_FORMAT_XRGB8888` 的字符是 `XR24`（`0x34325258`），`DRM_FORMAT_NV12` 的字符是 `NV12`（`0x3231564E`）。**一帧上百万像素，格式标识只记一次。**

线性 `XRGB8888` 一个像素占 4 字节，按小端布局从低地址到高地址是 **B、G、R、X**（X 是填充）。逻辑色值 R=12、G=34、B=56（十六进制）可存成 `56 34 12 A5`——A5 是原文实验的标记字节，不参与颜色运算。注意 `XR24` 的**颜色深度是 24 位，存储却是 32 位**：按 3 字节走，第二个像素就已经错位。

而且「RGB」还得先问是哪一层：DRM 格式、V4L2 内存格式，还是屏幕总线格式——三个语境下的字节序并不一致（上一篇已列过对照表）。

换成 NV12：亮度样本各 1 字节；色度平面每个网格位置占 2 字节，先 Cb 后 Cr；每个 2×2 亮度区域对应一对色度样本。所以内核格式表里是 `num_planes = 2`、`cpp = {1, 2}`、`hsub = vsub = 2`——**`cpp[1] = 2` 指每个色度平面位置占 2 字节**。整帧紧排时平均 1.5 字节/像素，这个平均数适合估数据量，**不能拿来给 (x,y) 寻址**。

## 三、Pitch 量的是两个行首之间的距离

实验 A：宽 3、高 2 的 XRGB8888，每行有效 `3 × 4 = 12` 字节；行距设为 16、图像从对象偏移 8 开始。两行行首分别在 8 和 24，第一行 12 字节之后要跨过 4 个填充字节。

```text
线性、单平面、每像素 B 字节：
像素首字节偏移 = 平面 offset + y × pitch + x × B

(2,1)：8 + 1 × 16 + 2 × 4 = 32
对象中 [32,36) 的实际字节：56 34 12 A5
```

若误把 12 当 pitch：y=0 时第一行全部读对，所以**只测第一行发现不了**；到第 y 行，两个行首之间已累计差 `y × (真实 − 误用)` 字节——这就是「行行错开」的来历。

行尾留空是硬件和对齐的常见结果，但要和第 3 篇的行消隐分清：**padding 在内存里占字节，消隐在输出时序里占时钟周期**，内存多出的 4 字节不会变成屏幕上的 4 个像素。具体取回多少要问创建这块内存的接口：这一版 Rockchip 的 `rockchip_gem_dumb_create()` 把普通 dumb buffer 的 pitch 按 **64 字节**向上对齐；`rockchip_fb_create()` 则检查传入 FB 的有效平面 pitch 是否为 **4 字节的倍数**。一个是分配器创建时给的结果，一个是驱动导入时检查的条件——**给定后者推不出摄像头一定按 4 或 64 字节分配**。

实验 A 的 16 是样本指定的行距，3×2 的尺寸只为逐字节读图；这版 VOP 对小于 4×4 的源/目标矩形另有最小尺寸处理，**不能拿这张小图的大小验证板上可见输出**。

## 四、Offset 从哪个对象开始数

实验 B：一块 104 字节内存装 8×4 NV12，两个格式平面共用一个对象，Y 从 16、UV 从 80，pitch 都是 12，两平面之间故意留了空隙（模拟能显式传各平面偏移的 FB）。注意 V4L2 连续格式 `V4L2_PIX_FMT_NV12` 有自己的连续排列约定，**不能把这份带间隙的教学布局当成该格式的默认排布**。

| 对象区间 | 内容 |
| --- | --- |
| `[0,16)` | 对象前缀 |
| `[16,64)` | Y 的四行，每行 8 有效 + 4 填充 |
| `[64,80)` | 两平面间隙，本例填 `DD` |
| `[80,104)` | UV 的两行，每行 4 对 CbCr，8 有效 + 4 填充 |

取亮度坐标 (5,3)：第 4 条亮度行、第 6 个位置；所属色度网格为 `(5 // 2, 3 // 2) = (2,1)`——这里定位的是对应存储样本，显示时的插值是下一层问题。

```text
Y  = 16 + 3 × 12 + 5             = 57
Cb = 80 + 1 × 12 + 2 × 2         = 96
Cr = Cb + 1                      = 97
```

57、96、97 处实际读到 `E0 60 A0`。若用 `offY + 宽 × 高 = 48` 当 UV 起点，同样算法会跑到 64、65，读到 `DD DD`；即便知道 pitch 改成 `offY + pitchY × 高 = 64`，仍漏掉 16 字节的平面间隙。**只有生产端确实规定 UV 紧跟完整 Y 存储区时，才能从 Y 的存储高度和行距推 UV 起点**——能拿到 `offsets[1]` 就直接用它。

真实画面的差值可以更大：1080p NV12 若 Y 的 pitch 是 2048、存储高度对齐到 1088、Y 偏移 0、UV 紧随这 1088 行，则 UV 起点是 `2048 × 1088 = 2,228,224`；把可见高度 1080 代进去会**早 16,384 字节**，再用可见宽度 1920 替行距，偏得更多。换分配器，存储高度和间隔都要重新确认。

## 五、两个平面、两个 fd、两个窗口，各在数什么

实验 B 也可以拆开存：Y 区搬到对象 A 开头、UV 区搬到对象 B 开头，同一点 (5,3) 变成 **A 的 41、B 的 16 和 17**。能独立算出这两个数，才算真正理解 offset 的参照点。

| 场合 | 「plane」或编号实际指什么 |
| --- | --- |
| DRM framebuffer 的格式平面 | 一个布局里的取数区域：线性 NV12 的槽 0 是 Y、槽 1 是 UV |
| V4L2 的 memory plane | 队列里分别描述/映射/导出的内存单元：`NV12` 可放一个单元，`NV12M` 可分开 |
| KMS plane | 能独立选 FB、源矩形、目标矩形的显示平面：一个 Win0 就能读 NV12 的两个格式平面 |
| DMA-BUF fd / GEM handle / FB ID | 分别指向共享缓冲、某个 DRM 打开实例里的对象句柄、已登记的 framebuffer |

同一个 GEM handle 可以同时填进 `handles[0]` 和 `handles[1]`，两槽靠各自的偏移与行距定位；若是两个对象，就填两个 handle。**两个不同的 fd 也可能因复制传递而引用同一底层对象**——不能靠比较 fd 整数判断内存是否相同。这里说「同一对象」是在谈寻址基准；物理页是否连续、设备通过哪个 DMA 地址访问，是映射层的问题。

从 V4L2 往 DRM 接时，几个同名 offset 尤其要辨清：

| 采集侧字段 | 转到显示侧怎么读 |
| --- | --- |
| `bytesperline` | 按实际协商格式解释字节行距；单内存平面的 NV12 还要按格式定义拆出 Y/UV |
| `sizeimage` / `v4l2_plane.length` / `bytesused` | 分别指格式所需容量、当前内存平面容量、当前载荷占用——**总数不足以反推各区起点** |
| `v4l2_plane.data_offset` | 本内存平面内图像数据起点；`bytesused` 包含它；还要厘清该平面怎样对应到导入的对象 |
| `v4l2_buffer.m.offset` / `v4l2_plane.m.mem_offset` | MMAP 模式交给 `mmap()` 定位用的参数；**填到 DRM 的 `offsets[]` 参照点就错了** |

另外 `V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE` 只说明节点用了多平面 API，实际返回几个内存平面要看协商后的格式与 `num_planes`。跨框架交接时，**记录每个 DRM 槽对应哪个导出对象，比只记一句「摄像头给了 NV12」有用得多**。

## 六、换成瓦片，同一个坐标为什么从 21 挪到 25

线性布局能按行扫；另一种做法是把二维图像切成小矩形，先存一个矩形内部、再存下一个——处理邻近区域时可能改善局部性，但顺着内存读到的下一个字节会跳到另一条图像行。

给每个像素 1 字节、宽 8 高 4 无填充：线性时 (5,2) 偏移 `2 × 8 + 5 = 21`；规定瓦片 4×2、瓦片间按行排、瓦片内也按行排，全图横向 2 块、每块 8 字节，目标在第 2 排第 2 块（块号 3）、块内坐标 (1,0)，于是 `3 × 8 + 0 × 4 + 1 = 25`。**两份内存都是 32 字节、分辨率与位深也相同，只有排列方式变了。**

在 DRM 里，**FourCC 与 modifier 合起来才标识一种具体布局**：modifier 是 64 位标识，`DRM_FORMAT_MOD_LINEAR` 为 0；分块改变的是「二维位置 → 存储位置」的映射；有些压缩布局还引入块头、辅助平面或特殊对齐。注意分块可以完全不压缩（刚才的例子仍占 32 字节），而 AFBC 是按其规则编码的压缩，消费方必须支持对应的 FourCC + modifier 组合——**线性 NV12 的两个地址公式读不了 AFBC，改个标签也不会重排内存**。

这里有个容易忽略的零：通过 `ADDFB2` 显式提交布局时，设 `DRM_MODE_FB_MODIFIERS` 并把在用槽的 modifier 填 0，表达的是**明确选择 LINEAR**；不设该标志走的是隐式约定，**不能把「没给 modifier」当作来自任意生产端的线性保证**。在这一版内核里，未设标志却填非零 modifier 会被 `framebuffer_check()` 拒绝；`DRM_FORMAT_MOD_INVALID` 只能作哨兵，不能当真实布局提交。还有一条约束：虽然 `modifiers[4]` 看着每平面可选一种，**这个 KMS 接口要求同一 FB 的所有有效槽填同一个 modifier**，未用槽清零——而 0 也是合法偏移，**仅凭 `offsets[i] == 0` 断定该槽未用是错的**。

## 七、从 DMA-BUF 到 FB ID，再到一次显示提交

共享内存只完成一半，另一半是把真实的布局描述带过去，让目标硬件按同样规则解释。应用可以先查目标 KMS plane 的 `IN_FORMATS`——它列的是 **FourCC 与 modifier 的配对能力**。看到支持格式 A、也看到某 modifier M，**不能把两列随意组合成「支持 A + M」**。

以实验 B 的单对象布局为例，调用边界是这样的：

```c
int add_sample_fb(int drm_fd, uint32_t handle, uint32_t *fb_id)
{
    const uint32_t handles[4]  = { handle, handle, 0, 0 };
    const uint32_t pitches[4]  = { 12, 12, 0, 0 };
    const uint32_t offsets[4]  = { 16, 80, 0, 0 };
    const uint64_t modifiers[4] = {
        DRM_FORMAT_MOD_LINEAR, DRM_FORMAT_MOD_LINEAR, 0, 0
    };

    return drmModeAddFB2WithModifiers(drm_fd, 8, 4, DRM_FORMAT_NV12,
                                      handles, pitches, offsets, modifiers,
                                      fb_id, DRM_MODE_FB_MODIFIERS);
}
```

两处 handle 相同，因为两部分属于同一对象。成功后 `*fb_id` 只是一个数字 ID——**它没有选 Win0，也没告诉显示端画在屏幕什么位置**。拆成两个对象时，数组要换成两个已导入的 handle 和两个零偏移。

这一版 Rockchip 内核里，这段调用可沿三层读下去：

1. **登记前的通用校验**：`drm_mode_addfb2_ioctl()` → `drm_mode_addfb2()` → `drm_internal_framebuffer_create()` → `framebuffer_check()`，查格式、尺寸、在用槽的 handle、最低行距、显式 modifier 的一致性（比如 8 像素宽的线性 Y 行只给 4 字节 pitch，已经装不下一行）
2. **驱动查对象**：`rockchip_fb_create()` 要求有效平面 pitch 按 4 字节对齐；随后 `drm_gem_fb_init_with_funcs()` 用当前 DRM 文件和 handle 查 GEM 对象，按各平面的尺寸/行距/偏移校验容量再初始化 FB
3. **放上窗口**：设 plane 的 `FB_ID`/`CRTC_ID`/`SRC_*`/`CRTC_*`，先 `DRM_MODE_ATOMIC_TEST_ONLY` 校验格式与 modifier 组合、矩形、缩放；通过后真实提交才安排更新。采集与显示循环用同一组缓冲时，还要等生产者写完、显示端用完再交还

一个很有判别力的反例：实验 B 的正确 UV 起点是 80，**谎报成 48 时行距仍合法、对象也够大，驱动照样接受描述，取样却读错**。反过来，真实有效的 NV12 也可能在窗口检查时失败，因为送错了不接受 NV12 的窗口。定位时先记录失败发生在**导入、建 FB、TEST_ONLY、真实提交，还是已经出图之后**。

## 八、RV1126B 把这些字段写进 VOP

按官方 `develop-6.1` 提交 `77168c8d` 读源码：`rockchip_vop_reg.c` 里从 `rv1126b_vop.win` 找到复用的 `rv1126_vop_win_data`——**Win0 是 overlay，格式表 `formats_win_full` 含 NV12；Win2 是 primary，`formats_win_lite` 列的是 RGB 家族**。做摄像头直显，抢到空闲 plane 还不够，必须看这个 plane 能取什么格式。

`vop_plane_atomic_check()` 从 `fb->obj[0]`、`fb->obj[1]` 分别取 Rockchip 对象的**设备 DMA 地址**，再叠加各平面 offset 与裁剪位移——启用 IOMMU 时它可能是 IOVA，**读应用进程里的 CPU 指针拿不到这个值**。

仍用 1080p 那组条件（两平面共用对象、pitch 均 2048、UV 起点 2,228,224），要从源图 (160,90) 开始显示 640×360：

```text
Y 首字节  = 对象 DMA 基址 + offY  + 90 × 2048 + 160
          = 对象 DMA 基址 + 184,480
UV 首字节 = 对象 DMA 基址 + offUV + 45 × 2048 + 80 × 2
          = 对象 DMA 基址 + 2,320,544
```

色度横坐标从 160 变 80，但每个位置 2 字节，横向位移仍是 160。代码里的 `src->x1`/`src->y1` 是 16.16 定点源坐标，算整数像素要 `>> 16`。**这一版 VOP 会拒绝裁剪后左边界为奇数像素的 YUV 源矩形**——第 4 节用 CPU 在完整帧里取奇坐标 (5,3) 完全可行，那是「找一个点」，与「把奇数横坐标交给硬件当窗口起点」是两件事。还有一处常见重复：先把裁剪位移并进 `offsets[]`，提交时又保留同一组非零源坐标，位移就算了两遍。

`vop_plane_atomic_update()` 里，`yrgb_mst`/`uv_mst` 拿前面算好的设备地址，`yrgb_vir`/`uv_vir` 拿 `DIV_ROUND_UP(fb->pitches[i], 4)`——**API 给的是字节，VOP 这两个行距寄存器以 4 字节为单位**。实验 B 的 12 折成 3，1080p 的 2048 折成 512；应用若「为了配合硬件」先自己除一次，就是把错单位交给了 DRM。

最后是一个从全仓库搜索容易得出相反结论的问题：`rockchip_drm_fb.c` 里确实有 AFBC 的处理代码，但**这一固定版本里 RV1126B 的这两个窗口条目没有绑定 AFBC modifier 表**；该注册路径下，DRM 对未提供列表且启用 modifier 的 plane 采用默认 LINEAR 列表，而 Rockchip 对非线性的 AFBC 检查还要核对它是否在目标 plane 的 modifier 表内。所以**按这份窗口配置，Win0 与 Win2 对各自格式声明的都是线性布局**。板上哪条路径能直扫压缩帧，要查运行内核对应窗口的 `IN_FORMATS`；拿到不能读的布局时，让上游改产兼容布局，或由支持双方格式的转换单元实际写出一份线性目标图。

## 九、同一张图为什么既是 48 字节，又是 104 字节

实验 B 只有 32 个 Y 字节 + 16 个 UV 字节 = **48 字节有效像素数据**，却散布在 104 字节的对象里。检查一次读取是否越界，要找最远的有效字节；分配设备可用缓冲，要服从分配器与硬件的完整要求。

```text
end = offset + (rows − 1) × pitch + rowBytes
最后一个有效字节偏移 = end − 1
```

| 平面 | 代入 | 最后有效字节 | 覆盖所需最小长度 |
| --- | --- | --- | --- |
| A 的 XRGB | 8 + 1×16 + 12 | 35 | 36（对象实际 40） |
| B 的 Y | 16 + 3×12 + 8 | 59 | 60 |
| B 的 UV | 80 + 1×12 + 8 | 99 | 100（与 Y 共用 104 字节对象） |

两个平面共用一个对象，就各自从**同一对象起点**校验，取最大的排他结束位置；分别用两个对象，就分别与各自容量比较。**把 60 和 100 相加，等于把同一基准之前的字节重复计数。** 这版 Rockchip 的 GEM framebuffer helper 还会用最后一行最小行宽参与容量校验。移植成 C 代码时乘加要用足够宽的整数并检查溢出——这个几何公式能检查活动样本范围，**替代不了硬件分配器**。

## 十、实操：把 pitch 从 12 改成 8，看哪一行最先出错

资料包根目录执行 `python3 examples/layout_probe.py --out probe-results`（Python 3.8+，不需要开发板），会生成 `xr24-3x2-p16.bin`、`nv12-8x4-p12.bin` 与对照图，并打印目标像素、正确/错误步长下的各行字节、瓦片地址表。

四个行首：正确是 16、28、40、52，误用 8 是 16、24、32、40。观察结果很说明问题：

- **第一行两幅完全相同**
- 第二行（y=1）开始，把上一行末尾的 4 个 `EE` 填充读进了画面
- 第三行（y=2）又在行尾读到 4 个 `EE`
- 第四行（y=3）误算的行首 40 恰好是真实第三行起点，**整行读出的都是合法像素，行号却错了**

所以那句话值得记住：**每个字节看起来都像合理的亮度，并不能证明它来自正确的位置。**

| 看到的现象 | 先做哪个区分度高的检查 |
| --- | --- |
| 首行对，后面斜着走或某几行错位 | 在原始数据上核对第 0、1、末行行首；分别用真实 pitch 与有效行宽计算，看误差是否随行号累积 |
| 灰阶轮廓对，彩块位置或颜色异常 | 对同一已知坐标查 Y、Cb、Cr 的对象与偏移；字节对上后再查 NV12/NV21 次序、矩阵与量程 |
| 图像呈固定周期的块状重排 | 让上游产生明确的线性测试图对比，并查两端声明的 FourCC:modifier 组合 |
| PRIME 导入成功，ADDFB2 或 atomic 失败 | 分别保留错误码与参数，先核 handle 所属 DRM 文件、对象大小、pitch、offset，再核目标 plane 的 `IN_FORMATS` 与几何 |

板上可用 `v4l2-ctl -d /dev/videoX --get-fmt-video` 看采集端协商结果、`modetest -M rockchip -p` 看 plane 格式与属性。`IN_FORMATS` 若是 blob，要用能解码的工具或 libdrm 的格式/modifier 迭代接口读配对；**同时记录程序实际传给 ADDFB2 的数组——只看驱动「支持什么」，还原不出本次「填了什么」**。

## 写在最后

回到开头那个 1080p 故障：把 Y 行距改成 2048，只解决了「下一条亮度行从哪读」。要判断残留的颜色异常，得从 UV 区挑一对已知样本——若它确实在 2,228,224 起算的位置，而程序仍按 2,211,840 去找，先修两平面的起始描述；等 Y、Cb、Cr 的取址全部对上，再去查上一篇讲的色差顺序、矩阵与量化范围。**一次只验证一个假设**，画面对了，也能说清是哪一行代码让它对的。

这篇和站内[《从 NV12 到 RGB888》](/posts/linux/nv12-rgb-color/)、[《Rockchip DRM/KMS 精读》](/posts/rk3588/drm-kms/)、[《零拷贝精读》](/posts/rk3588/zero-copy/) 是同一条线的三段：**布局（本篇）→ 颜色（上篇）→ 框架与缓冲（另两篇）**。显示链路的问题之所以难，往往不是数学难，而是「同一个词在不同层指不同的东西」——plane、offset、pitch、格式，每一层都有自己的参照点。
